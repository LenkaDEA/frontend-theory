**Пагинация через from_id (Cursor-based pagination)** — это метод постраничной навигации, при котором вместо указания смещения (`offset`) клиент передает серверу **уникальный идентификатор (курсор)** последнего полученного элемента. 

Сервер использует этот идентификатор как отправную точку, чтобы найти и вернуть следующие `N` элементов, идущих строго после него.

*   **Курсор (`from_id`, `after`, `cursor`)**: Уникальное значение (часто это ID записи, `created_at` timestamp или зашифрованная строка), которое однозначно определяет позицию элемента в отсортированном списке.
*   **Limit**: Сколько элементов нужно вернуть после этого курсора.

---

### 2. Как это работает (Под капотом: Фронтенд + Бэкенд/БД)

#### На стороне Фронтенда
Фронтенд больше не знает номеров страниц. Он знает только одно: "Какой элемент был последним в предыдущей порции данных?".

1.  **Первый запрос:** Фронтенд запрашивает данные без курсора (или с `from_id=0`/`null`).
    *   Запрос: `/api/items?limit=10`
    *   Ответ: Массив из 10 элементов. Последний элемент имеет `id: 456`.
2.  **Второй запрос:** Пользователь доскроллил до конца. Фронтенд берет ID последнего элемента (`456`) и отправляет его как курсор.
    *   Запрос: `/api/items?limit=10&from_id=456`
    *   Ответ: Массив из следующих 10 элементов. Последний элемент имеет `id: 420`.
3.  И так далее.

#### На стороне Бэкенда и Базы Данных
Это самое главное отличие. SQL-запрос меняется кардинально:

```sql
-- Предположим, мы сортируем по убыванию ID (новые сверху)
SELECT * FROM users 
WHERE id < 456 -- Вот она, магия курсора!
ORDER BY id DESC 
LIMIT 10;
```

**Почему это работает невероятно быстро:**
Базе данных больше не нужно сканировать и отбрасывать предыдущие записи. Если поле `id` проиндексировано (а первичные ключи всегда проиндексированы), база данных использует индекс (B-Tree), чтобы **мгновенно** найти запись с `id = 456`, и просто читает следующие 10 записей. 
Скорость выполнения запроса одинакова, запрашиваешь ты 1-ю "страницу" или 10 000-ю. Время выполнения — константа $O(1)$ относительно смещения.

### 3. Примеры использования (React и Vue)

Реализация на фронтенде идеально ложится на паттерн бесконечного скролла, который мы разбирали ранее.

#### Пример на React (с использованием Infinite Scroll)

```tsx
import { useState, useEffect, useRef } from 'react';

export const CursorPagination = () => {
  const [items, setItems] = useState([]);
  const [isLoading, setIsLoading] = useState(false);
  const [hasMore, setHasMore] = useState(true);
  
  // Храним курсор. Изначально null (для первого запроса)
  const [cursor, setCursor] = useState<string | null>(null);

  const fetchItems = async () => {
    if (isLoading || !hasMore) return;
    setIsLoading(true);

    try {
      // Формируем URL. Если курсор есть, добавляем его.
      const url = new URL('/api/items', window.location.origin);
      url.searchParams.append('limit', '10');
      if (cursor) {
        url.searchParams.append('from_id', cursor);
      }

      const response = await fetch(url.toString());
      const data = await response.json();
      
      if (data.items.length > 0) {
        setItems(prev => [...prev, ...data.items]);
        
        // ОБНОВЛЯЕМ КУРСОР: берем ID последнего элемента из пришедших данных
        const lastItem = data.items[data.items.length - 1];
        setCursor(lastItem.id);
      } else {
        // Если пришел пустой массив, значит данные кончились
        setHasMore(false);
      }
    } finally {
      setIsLoading(false);
    }
  };

  // Вызываем fetchItems при монтировании (первый запрос)
  useEffect(() => {
    fetchItems();
  }, []);

  // ... здесь логика IntersectionObserver, которая вызывает fetchItems(), 
  // когда пользователь доскроллил до конца (как в примере из первой темы)

  return (
    <div>
      <ul>
        {items.map(item => <li key={item.id}>{item.name}</li>)}
      </ul>
      {isLoading && <p>Загрузка...</p>}
      <button onClick={fetchItems} disabled={!hasMore || isLoading}>
        Загрузить еще
      </button>
    </div>
  );
};
```

#### Пример на Vue 3

```vue
<template>
  <div>
    <ul>
      <li v-for="item in items" :key="item.id">{{ item.name }}</li>
    </ul>
    <p v-if="isLoading">Загрузка...</p>
    <!-- Кнопка вместо обсервера для простоты примера -->
    <button @click="fetchItems" :disabled="!hasMore || isLoading">
      Загрузить еще
    </button>
  </div>
</template>

<script setup lang="ts">
import { ref, onMounted } from 'vue';

const items = ref([]);
const isLoading = ref(false);
const hasMore = ref(true);
const cursor = ref<string | null>(null);

const fetchItems = async () => {
  if (isLoading.value || !hasMore.value) return;
  isLoading.value = true;

  try {
    let url = `/api/items?limit=10`;
    if (cursor.value) {
      url += `&from_id=${cursor.value}`;
    }

    const response = await fetch(url);
    const data = await response.json();

    if (data.items.length > 0) {
      items.value.push(...data.items);
      // Обновляем курсор
      cursor.value = data.items[data.items.length - 1].id;
    } else {
      hasMore.value = false;
    }
  } finally {
    isLoading.value = false;
  }
};

onMounted(() => {
  fetchItems();
});
</script>
```

### 4. Тонкие моменты и возможные проблемы

Хотя курсорная пагинация решает проблемы `limit/offset`, у нее есть свои ограничения и нюансы реализации.

#### Проблема 1: Невозможность прыгнуть на произвольную страницу
С курсорной пагинацией вы не можете сделать UI вида `[1] [2] ... [10] [11]`. Вы не можете сказать бэкенду "дай мне 10-ю страницу", потому что вы не знаете, какой `from_id` будет в начале 10-й страницы, пока не загрузите все предыдущие 9.
*   *Следствие:* Этот подход подходит **только** для кнопок "Вперед/Назад" или бесконечного скролла.

#### Проблема 2: Сложность сортировки по не уникальным полям
В примере выше мы сортировали по уникальному `id`. А что если нам нужно отсортировать список пользователей по `rating` (рейтингу)?
Рейтинг не уникален (у Васи и Пети может быть рейтинг 5). Если мы сделаем запрос `WHERE rating < 5`, мы можем пропустить пользователей с таким же рейтингом.
*   *Решение на бэкенде:* Курсор должен быть составным (композитным). Бэкенд должен сортировать по `(rating, id)` и курсор должен содержать оба значения (например, зашифрован в base64 строку: `eyJyYXRpbmciOjUsImlkIjo0NTZ9`). Для фронтенда это просто непрозрачная строка (opaque string), которую он передает как есть.

#### Проблема 3: Удаление элемента-курсора
*   *Сценарий:* Фронтенд сохранил `cursor = 456`. Пока пользователь читал ленту, запись с `id = 456` удалили из базы данных. Пользователь скроллит вниз, фронтенд отправляет `from_id=456`.
*   *Решение:* Бэкенд должен быть написан правильно. Запрос `WHERE id < 456` все равно сработает корректно, даже если самой записи `456` уже нет в базе. База просто найдет первую запись, которая меньше `456`. (В отличие от `offset`, где удаление сдвигает весь список).

#### Главное преимущество (Решение проблемы Data Drift)
Курсорная пагинация **полностью решает проблему дублирования или пропуска элементов**, которая была в `limit/offset`.
Даже если во время чтения ленты в начало списка добавили 100 новых записей, запрос `WHERE id < 456` вернет ровно те записи, которые идут *после* элемента `456`. Новые записи сверху никак не повлияют на этот запрос. UI останется консистентным.

### Резюме для собеседования

*   **Limit/Offset:** Медленно на больших данных, баги с дублированием при добавлении новых записей. Подходит для таблиц с номерами страниц.
*   **Cursor (from_id):** Работает мгновенно на любых объемах (благодаря индексам БД), гарантирует отсутствие дублей при добавлении данных. Идеально для бесконечного скролла. Минус — нельзя прыгнуть на конкретную страницу.

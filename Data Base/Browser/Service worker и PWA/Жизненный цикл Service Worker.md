#### 1. Определение
Жизненный цикл Service Worker'а — это строгая последовательность состояний, которые он проходит от момента регистрации в коде до момента, когда он начинает контролировать страницу (перехватывать запросы) и до его удаления. Цель такого сложного цикла — **обеспечить, чтобы у пользователя никогда не сломался сайт в процессе обновления** (как в нативных приложениях: вы не можете обновить приложение, пока им пользуетесь).

#### 2. Как работает в браузере (Этапы жизненного цикла)

Давай разберем по шагам, что происходит, когда браузер впервые скачивает `sw.js` и когда появляется новая версия.

**Состояния Service Worker'а:**

1.  **Parsed (Разобран)**
    Браузер скачивает файл `sw.js` (вызванный через `navigator.serviceWorker.register()`) и парсит JS-код. Если в коде синтаксическая ошибка — процесс останавливается.
2.  **Installing (Устанавливается)** — *Событие `install`*
    Если парсинг успешен, запускается событие `install`.
    *Для чего используется:* Здесь мы кэшируем статические ассеты (App Shell — HTML, CSS, JS, логотипы), необходимые для оффлайн-работы.
    *Важно:* Если хотя бы один файл не скачался и не попал в кэш, установка **прерывается**.
3.  **Installed / Waiting (Установлен / Ожидает)**
    SW успешно установлен. Но он **еще не контролирует страницу**.
    Если это первая установка (раньше SW не было), он сразу переходит к следующему шагу.
    Но если у юзера **уже работает старая версия SW**, новый SW переходит в состояние **Waiting**. Он ждет, пока пользователь закроет **все** вкладки этого сайта. (Перезагрузка страницы по умолчанию не поможет!).
4.  **Activating (Активируется)** — *Событие `activate`*
    Наступает, когда старый SW ушел (все вкладки закрыты) или это первый запуск.
    *Для чего используется:* Идеальное место для **очистки старого кэша**. Старый SW уже не контролирует приложение, новый вступает в права — значит, можно удалить закэшированные файлы от прошлой версии.
5.  **Activated (Активирован)**
    Теперь SW полностью контролирует страницу и готов перехватывать функциональные события: `fetch` (сетевые запросы), `push` (уведомления), `sync` (фоновая синхронизация).
    *Нюанс:* При первой установке страница, которая зарегистрировала SW, **не контролируется им до следующей перезагрузки**.
6.  **Redundant (Устаревший)**
    SW отправляется на свалку. Это происходит, если:
    *   Установка провалилась.
    *   Активация провалилась.
    *   Появился новый SW, и этот старый был заменен.

#### 3. Пример использования (React/Vue/TS)

Давай посмотрим, как эти события обрабатываются внутри самого `sw.ts` (или `sw.js`):

```typescript
/// <reference lib="webworker" />
const sw = self as unknown as ServiceWorkerGlobalScope;

const CACHE_NAME = 'app-v1'; // При обновлении сайта меняем на app-v2
const ASSETS_TO_CACHE = [
  '/',
  '/index.html',
  '/styles.css',
  '/main.js'
];

// Этап 1: INSTALL
sw.addEventListener('install', (event) => {
  console.log('[SW] Installing...');
  
  // event.waitUntil() говорит браузеру: "Не завершай этап установки, 
  // пока этот Promise не выполнится"
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then((cache) => {
        console.log('[SW] Caching App Shell');
        return cache.addAll(ASSETS_TO_CACHE); // Загружаем файлы в кэш
      })
  );
  
  // Опционально: заставить SW активироваться сразу, не дожидаясь закрытия вкладок
  // sw.skipWaiting(); 
});

// Этап 2: ACTIVATE
sw.addEventListener('activate', (event) => {
  console.log('[SW] Activating...');
  
  // Удаляем старые кэши (app-v1), оставляем только текущий (app-v2)
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames.map((cacheName) => {
          if (cacheName !== CACHE_NAME) {
            console.log('[SW] Deleting old cache:', cacheName);
            return caches.delete(cacheName);
          }
        })
      );
    })
  );
  
  // Опционально: заставить SW взять под контроль текущие открытые страницы немедленно
  // sw.clients.claim();
});

// Этап 3: Работа (перехват запросов)
sw.addEventListener('fetch', (event) => {
  // ... логика кэширования (разберем в следующем блоке)
});
```

#### 4. Тонкие моменты и нюансы (Ошибки новичков)

1.  **Проблема "Зомби-вкладок" (самая частая):**
    *   *Проблема:* Ты выкатил новый релиз. Юзер сидит на сайте, обновляет страницу (F5), но видит старый дизайн.
    *   *Почему:* Потому что новый SW скачался, установился, но завис в состоянии **Waiting**. Чтобы он активировался, нужно чтобы счетчик клиентов упал до нуля (нужно закрыть вкладку, а не просто перезагрузить).
    *   *Решение:* Использовать метод `skipWaiting()`. Часто делают так: со стороны React/Vue приложения ловят событие обновления SW и показывают пользователю плашку "Доступна новая версия, обновить?". Если юзер жмет "Да", в SW посылается сообщение `postMessage({ type: 'SKIP_WAITING' })`, SW вызывает `self.skipWaiting()`, обновляется и перегружает вкладку. Библиотека `vite-plugin-pwa` в React/Vue делает это из коробки параметром `prompt for update`.

2.  **event.waitUntil():**
    *   *Ошибка:* Выполнять асинхронный код в `install` или `activate` без использования `event.waitUntil()`.
    *   *Нюанс:* Как мы обсуждали в [ранее](Базовые%20концепции.md), браузер может убить процесс SW в любую секунду. Если ты делаешь запрос или пишешь в кэш асинхронно, SW умрет до того, как Promise зарезолвится. `event.waitUntil()` — это "замок", который говорит браузеру держать процесс живым, пока промис не выполнится.

3.  **Первая загрузка не контролируется:**
    *   *Проблема:* Юзер впервые зашел на сайт. SW установился и активировался. Но если нажать "Оффлайн", картинки могут не прогрузиться, если их нет в предкэше.
    *   *Почему:* При первом заходе страница загрузилась *до* того, как SW взял над ней контроль. Текущие запросы на этой странице он не перехватывает.
    *   *Решение:* В событии `activate` вызвать `self.clients.claim()`. Это заставляет SW немедленно взять под контроль все открытые страницы, не дожидаясь их перезагрузки. (Часто используется в связке со `skipWaiting()`).

4.  **Размер кэшируемых файлов на этапе `install`:**
    *   *Ошибка:* Пытаться засунуть в `cache.addAll()` во время `install` слишком много файлов (сотни картинок).
    *   *Нюанс:* Если хотя бы один файл из массива вернет 404, весь процесс `install` упадет, и SW перейдет в состояние *Redundant*. В `install` кэшируют только критический минимум (App Shell: index.html, css, js). Остальное — динамически в процессе работы.

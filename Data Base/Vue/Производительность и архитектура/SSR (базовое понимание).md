#### 📝 Определение
**SSR (Рендеринг на стороне сервера)** — это процесс, при котором HTML-страница приложения генерируется (собирается из компонентов) **на сервере** (обычно на Node.js), а не в браузере пользователя. Браузер получает уже готовый HTML с контентом, а затем "оживляет" его с помощью JavaScript (этот процесс называется **гидратацией** / hydration).

**Обычное SPA (Single Page Application - CSR, Client-Side Rendering):**
1. Браузер скачивает пустой `index.html` (`<div id="app"></div>`).
2. Браузер скачивает тяжелый `bundle.js`.
3. Vue/React запускается в браузере, делает запросы к API, строит DOM.
*Итог:* Пользователь видит белый экран (или лоадер), пока всё это происходит. SEO-роботы (особенно старые) могут увидеть пустую страницу.

**SSR:**
1. Пользователь запрашивает страницу.
2. Сервер (Node.js) запускает Vue/React, делает запросы к API, генерирует строку HTML с готовыми данными.
3. Браузер мгновенно показывает этот HTML пользователю (быстрый FCP - First Contentful Paint).
4. В фоне скачивается JS и "привязывается" к готовому HTML (гидратация), чтобы кнопки начали нажиматься.

#### ⚖️ Сравнение с React
Концепция абсолютно одинаковая.
*   **React:** Для SSR стандартом де-факто является фреймворк **Next.js** (или Remix).
*   **Vue:** Для SSR стандартом де-факто является фреймворк **Nuxt.js** (Nuxt 3).

Писать SSR "руками" (на голом Vue или React + Express) — это боль, так как нужно вручную настраивать сборку для сервера и клиента, роутинг, управление состоянием (чтобы данные с сервера передались на клиент). Поэтому на собеседовании, когда говорят про SSR во Vue, почти всегда подразумевают **Nuxt**.

#### 🛠 Как использовать (Особенности работы)

В SSR-приложении твой код выполняется **дважды**: один раз на сервере (чтобы сгенерировать HTML) и один раз в браузере (при гидратации). Из-за этого меняется подход к написанию кода.

**Пример (Nuxt 3 / Vue 3):**

```html
<script setup>
// 1. Получение данных
// В Nuxt мы используем useAsyncData или useFetch вместо обычного fetch/axios.
// Этот запрос выполнится НА СЕРВЕРЕ. Клиенту придет уже готовый HTML + JSON с этими данными,
// поэтому браузер не будет делать повторный запрос при загрузке страницы.
const { data: article } = await useFetch('https://api.example.com/articles/1')

// 2. Доступ к браузерным API
// ОШИБКА: console.log(window.innerWidth) - упадет на сервере, так как там нет window!

// ПРАВИЛЬНО:
import { onMounted } from 'vue'

onMounted(() => {
  // onMounted (и onBeforeMount) выполняются ТОЛЬКО в браузере!
  // Здесь безопасно обращаться к window, document, localStorage и т.д.
  console.log('Ширина экрана:', window.innerWidth)
})
</script>

<template>
  <article>
    <!-- Этот заголовок будет в исходном HTML, который придет с сервера -->
    <h1>{{ article.title }}</h1>
    <p>{{ article.content }}</p>
  </article>
</template>
```

#### ⚠️ Особенности и ловушки (Pitfalls) для собеседования

Это самое важное! На собеседованиях по SSR всегда спрашивают про эти "грабли":

1. **Отсутствие браузерных API на сервере:**
   *Проблема:* Ты пытаешься прочитать `localStorage` или обратиться к `window`/`document` прямо в теле `<script setup>`. На сервере (Node.js) этих объектов нет, и приложение упадет с ошибкой `window is not defined`.
   *Решение:* Оборачивать такой код в хук `onMounted` (он не вызывается на сервере) или использовать проверки вроде `if (typeof window !== 'undefined')` (в Nuxt есть встроенный флаг `import.meta.client` или `process.client`).

2. **Ошибки гидратации (Hydration Mismatch):**
   *Проблема:* HTML, который сгенерировал сервер, **не совпадает** с тем HTML, который Vue ожидает увидеть при запуске в браузере.
   *Пример:* На сервере ты отрендерил `<p>Сейчас: 12:00:01</p>` (время сервера). Через секунду в браузере Vue пытается гидратировать этот кусок и видит, что по его расчетам должно быть `<p>Сейчас: 12:00:02</p>`. Vue ругнется в консоль: *Hydration text mismatch*.
   *Решение:* Избегать рендеринга данных, которые зависят от окружения (время, случайные числа, данные из localStorage), до того, как приложение смонтируется (`onMounted`).

3. **Утечки памяти (Memory Leaks) на сервере:**
   *Проблема:* В браузере, когда пользователь закрывает вкладку, вся память очищается. На сервере процесс Node.js работает постоянно и обслуживает тысячи пользователей. Если ты создаешь глобальные переменные (например, глобальный объект стора, который не пересоздается для каждого запроса), данные одного пользователя могут "протечь" к другому, или сервер просто упадет от нехватки памяти (OOM).
   *Решение:* В SSR-фреймворках (Nuxt) сторы (Pinia) и роутеры создаются **заново для каждого входящего запроса**. Нельзя использовать синглтоны для хранения пользовательских данных вне контекста запроса.

4. **Зачем вообще нужен SSR? (Классический вопрос)**
   *Ответ:* 
	   1. **SEO (Поисковая оптимизация):** Поисковикам легче индексировать готовый HTML.
	   2. **SMO (Social Media Optimization):** Чтобы при шаринге ссылки в Telegram/Facebook генерировались красивые превью (OpenGraph теги), они должны быть в HTML изначально.
	   3. **Производительность (на слабых устройствах):** Пользователь быстрее видит контент (улучшаются метрики Core Web Vitals, особенно LCP).

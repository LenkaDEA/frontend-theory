#### Архитектурная теория

Pinia — это не самостоятельный движок реактивности (в отличие от MobX, который имеет собственное ядро). Pinia — это элегантная обертка над Reactivity API самого Vue 3 (`@vue/reactivity`).

1. State (Состояние):
    - _Под капотом:_ Когда ты объявляешь `state` в Options API, Pinia пропускает возвращаемый объект через функцию `reactive()` из Vue. В Setup API ты сам используешь `ref()` или `reactive()`.
    - _Механика:_ `reactive()` создает JavaScript Proxy. Когда компонент читает свойство (например, `store.user.name`), Proxy перехватывает операцию `get` и регистрирует этот компонент как "подписчика" (зависимость). Когда ты меняешь свойство, Proxy перехватывает `set` и уведомляет всех подписчиков о необходимости рендера.
    
2. Getters (Вычисляемые свойства):
    - _Под капотом:_ Геттеры — это буквально обертки над `computed()` из Vue.
    - _Механика (Кэширование):_ Как и `computed`, геттеры в Pinia ленивы и кэшируются. Функция геттера не выполнится, пока к ней кто-то не обратится. После первого вычисления результат кэшируется. Vue запоминает, какие реактивные зависимости (части `state`) использовались внутри геттера. Геттер пересчитается _только тогда_, когда изменится одна из его зависимостей. Если зависимости не менялись, при повторном обращении мгновенно вернется кэшированный результат.
    
3. Actions (Действия):
    - _Под капотом:_ Это просто обычные JavaScript-функции.
    - _Механика:_ В Options API Pinia автоматически привязывает контекст `this` этих функций к инстансу стора (тому самому Proxy-объекту). В Setup API они работают через замыкания (closures), обращаясь к `ref`/`reactive` переменным напрямую. Никакой магии диспетчеризации (как `dispatch` в Redux/Vuex) здесь нет.

#### Аналогия с MobX / React

- State:
    - _MobX:_ Аналог `@observable` или `makeAutoObservable`.
    - _React:_ Аналог `useState` или стейта внутри `useReducer`.
- Getters:
    - _MobX:_ Точный аналог `@computed`. Та же логика ленивости, отслеживания графа зависимостей и кэширования.
    - _React:_ Аналог `useMemo`. Но в React ты должен вручную указывать массив зависимостей (`[state.a, state.b]`). В Pinia (как и в MobX) зависимости определяются _автоматически_ во время выполнения.
- Actions:
    - _MobX:_ Аналог `@action`. В MobX экшены нужны для батчинга обновлений (чтобы не рендерить UI на каждое изменение свойства). Во Vue 3 батчинг обновлений DOM встроен в сам цикл рендеринга (nextTick), поэтому экшены в Pinia — это просто удобный способ инкапсулировать бизнес-логику.
    - _React:_ Обычные функции внутри кастомного хука, которые вызывают `setState`.

#### Best Practices & TypeScript

- Передача аргументов в Getters: По умолчанию геттеры не принимают аргументов (они опираются только на стейт). Если тебе нужно передать аргумент, геттер должен вернуть _функцию_. Важно: В этом случае результат выполнения возвращаемой функции _не кэшируется_ (кэшируется только сама функция).
- Доступ к другим сторам: Внутри геттеров и экшенов можно безопасно импортировать и использовать другие сторы.
- Типизация `this` в Options API: TypeScript иногда теряет тип `this` внутри геттеров, если ты явно указываешь тип возвращаемого значения и используешь `this` одновременно. В таких случаях лучше использовать первый аргумент `state`.

#### Главный "подводный камень"

Геттеры, возвращающие функции (потеря кэширования). Частая ошибка — думать, что если геттер возвращает функцию для фильтрации с аргументом, то результат фильтрации будет закэширован.
```ts
// Options API пример
getters: {
  // ❌ Результат вызова getUserById(1) НЕ кэшируется! 
  // Функция будет выполняться заново при каждом рендере компонента.
  getUserById: (state) => {
    return (userId: string) => state.users.find(u => u.id === userId)
  }
}
```
_Решение:_ Если нужна сложная фильтрация с аргументами и кэшированием, лучше вычислять производные данные в `computed` внутри самого компонента, либо использовать мемоизацию (например, `lodash/memoize`) внутри геттера.

#### Пример кода

Покажу нюансы типизации и работы с геттерами в Setup-стиле (как наиболее актуальном).

```ts
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

interface Todo {
  id: number
  text: string
  isDone: boolean
}

export const useTodoStore = defineStore('todos', () => {
  // --- State ---
  const todos = ref<Todo[]>([])
  const filter = ref<'all' | 'completed' | 'active'>('all')

  // --- Getters ---
  
  // 1. Обычный геттер. КЭШИРУЕТСЯ. 
  // Пересчитается только если изменится массив todos.
  const completedTodos = computed(() => {
    console.log('Вычисляем completedTodos...') // Сработает только 1 раз до изменения стейта
    return todos.value.filter(t => t.isDone)
  })

  // 2. Геттер, зависящий от другого геттера и стейта. КЭШИРУЕТСЯ.
  const filteredTodos = computed(() => {
    if (filter.value === 'completed') return completedTodos.value
    if (filter.value === 'active') return todos.value.filter(t => !t.isDone)
    return todos.value
  })

  // 3. Геттер с аргументом (возвращает функцию). НЕ КЭШИРУЕТ результат вызова!
  // Используй с осторожностью в шаблонах (template).
  const getTodoById = computed(() => {
    return (id: number): Todo | undefined => {
      return todos.value.find(t => t.id === id)
    }
  })

  // --- Actions ---
  function addTodo(text: string) {
    todos.value.push({
      id: Date.now(),
      text,
      isDone: false
    })
  }

  function toggleTodo(id: number) {
    const todo = getTodoById.value(id) // Использование геттера внутри экшена
    if (todo) {
      todo.isDone = !todo.isDone // Прямая мутация стейта
    }
  }

  return {
    todos,
    filter,
    completedTodos,
    filteredTodos,
    getTodoById,
    addTodo,
    toggleTodo
  }
})
```
